# Milestone v1.3: Hermes-First Autonomous Company Interface

**Status:** SHIPPED 2026-05-05
**Phases:** 26-29
**Total Plans:** 11

## Overview

Profit-Corp Hermes v1.3 turns the previously shipped autonomous launch backbone into a single Hermes-first operator experience: one project-start entrypoint, internal role orchestration, one proposal-and-approval surface, and one final success-or-blocked outcome surface, all backed by the same governed delivery truth.

## Phases

### Phase 26: Hermes Intent Gateway and Unified Project Start

**Goal:** Let the owner tell Hermes to start a project without selecting scripts, phases, or transport-specific entrypoints.
**Depends on**: None
**Plans**: 3 plans

Plans:
- [x] 26-01: Normalize Hermes-native project-start requests into the existing governed run envelope
- [x] 26-02: Reuse the shipped bootstrap backbone through a Hermes-first startup adapter
- [x] 26-03: Render Hermes-native startup acknowledgements and blockers from persisted run truth

**Details:**
- Hermes-native startup now reuses the same authoritative run identity and bootstrap lifecycle as the existing governed chat-run path
- startup status is rendered in Hermes language while preserving direct access to authority artifacts underneath
- duplicate or malformed startup requests remain replay-safe and fail closed

### Phase 27: Hermes Internal Role Routing and Delivery Handoff

**Goal:** Keep all company and delivery roles behind Hermes so the owner talks to one system while Hermes coordinates the specialists.
**Depends on**: None
**Plans**: 3 plans

Plans:
- [x] 27-01: Persist durable internal role-routing traces and handoff targets
- [x] 27-02: Carry Hermes-internal handoff truth into the existing approved-delivery bundle
- [x] 27-03: Explain internal progress and blockers in Hermes-first language without exposing operator controls

**Details:**
- internal discovery, qualification, and delivery handoffs now record role identity, artifact output, and next handoff target durably
- approved-project bundles preserve Hermes-internal handoff context for downstream delivery governance
- owner-facing progress can mention the kind of work or responsible role without breaking the single-Hermes surface

### Phase 28: Hermes Proposal and Approval Surface

**Goal:** Present one proposal and one approval loop as a clean Hermes conversation surface while preserving the locked contract underneath.
**Depends on**: None
**Plans**: 3 plans

Plans:
- [x] 28-01: Render one concise Hermes proposal object from qualification and contract truth
- [x] 28-02: Map approve/reject replies into the existing governed approval model with strict linkage and idempotency
- [x] 28-03: Preserve the same locked delivery contract and reopen behavior under the conversational approval surface

**Details:**
- approved-project records now carry a single Hermes proposal object with pain point, target user, feasibility, pricing evidence, launch framing, and backlinks
- conversational approve/reject replies are parsed through a shared adapter and still persist through governed approval events
- approved proposals keep proposal identity, contract completeness, and drift/reopen behavior aligned with the existing delivery backbone

### Phase 29: Hermes Final Delivery Experience and Blocked Recovery

**Goal:** Make final success and blocked recovery feel like normal Hermes outputs from the same start-to-finish workflow.
**Depends on**: Phase 28
**Plans**: 2 plans

Plans:
- [x] 29-01: Lock the final approved-delivery status surface as the authoritative view model for shipped and blocked outcomes
- [x] 29-02: Lock Hermes-native final notifications against that same persisted truth source

**Details:**
- final status rendering already exposed deploy URL, final handoff path, final review path, blocked stage, blocked reason, repair action, and recovery detail from persisted authority
- final chat notifications already enforced truth convergence and idempotent replay; milestone work added regression coverage to make that contract explicit
- Hermes now ends the workflow with one success reply or one honest blocked-recovery reply, both derived from authoritative delivery state

## Milestone Summary

**Decimal Phases:**

- None

**Key Decisions:**
- Decision: Hermes should be the only intentional operator-facing surface while internal roles, scripts, and specialist stages remain implementation details
- Decision: All Hermes-native packaging must continue to reuse the existing governed run, approval, delivery, and recovery backbone rather than inventing a parallel state machine
- Decision: Approval and final delivery surfaces must remain truth-first and fail closed on ambiguity or incomplete evidence

**Issues Resolved:**
- removed the need for the owner to reason about scripts, phases, or transport-specific startup paths
- made internal role progress and delivery handoff inspectable without exposing those roles as user-operated tools
- collapsed proposal approval into one Hermes-native surface while preserving locked-contract governance
- locked final shipped success and blocked recovery against authoritative delivery truth instead of transient process memory

**Issues Deferred:**
- open-artifact audit still reports the legacy `Phase 11 / 11-HUMAN-UAT.md` entry despite zero pending scenarios; milestone close accepts it as deferred process debt
- richer chat-native retry, redirect, or cancel recovery commands remain future work beyond the current final blocked-recovery surface

**Technical Debt Incurred:**
- milestone close proceeded without a dedicated `v1.3-MILESTONE-AUDIT.md` artifact
- `roadmap.analyze` and `milestone.complete` automation still report roadmap completion/archive edge cases that required manual cleanup during closeout
